### Orchestrator code review — two residual risks (found by reading the implementation, not by tests)

Both are **latent**, not present-day defects. Every gate is green and neither is reachable today.
Recording them because both are the kind of thing that only bites later.

**1. `send-sms` does not pass `response=json`, so a plain-text error body could be read as success.**
`src/lib/notifications/sms.ts:40-50` builds the send URL with `action`/`api_key`/`to`/`from`/`sms`
but **not** `response=json` — whereas the verified balance check explicitly did pass it. If Arkesel
v1's `send-sms` returns plain text rather than JSON by default, then `response.json()` rejects,
`.catch(() => null)` sets `body = null`, and a `200` falls through both failure branches to
`{success: true}`. That degradation is *deliberate and correct* for an unknown-but-successful
response — but it also means the `code !== 'ok'` branch can **never fire** when the body is not
JSON. A logical failure returned as HTTP 200 with a plain-text error would therefore be mis-mapped
as a success. Two cheap hardening options, neither safe to pick without a real send to confirm the
default: pass `response=json` to force a JSON envelope, and/or fall back to `response.text()` when
JSON parsing fails so the body at least reaches the log. **This is the single most valuable thing
the pending one-off live send would settle.**

**2. Channel independence is conventional, not structural.**
`src/lib/notifications/index.ts:54-57` (and `:80-83`) awaits SMS and then WhatsApp sequentially with
no `try`/`catch` between them. This is safe *today* because every sender is contractually no-throw
(each wraps its own `fetch` in try/catch and returns a result object, and the pre-`fetch` code —
`process.env` reads and the pure `toGhanaE164` — cannot throw). But the "both channels always fire
independently" product decision currently rests on that convention holding. If any sender is ever
edited to throw, WhatsApp silently stops firing and no test targeting the *fan-out* would
necessarily catch it. `Promise.allSettled` would make the independence structural. Left as-is to
avoid unplanned scope, and because the current sequential style is what the file already used.

### Arkesel response-shape research (orchestrator, since no key exists to test with)

Since the empirical check was impossible, the shape was researched instead. Result: **it cannot be
pinned down authoritatively, and there are two incompatible candidate shapes in circulation.**

- **v2** (`POST /api/v2/sms/send` with the `api-key` header — what this feature uses) is reported
  as `{"status": "success", "data": { "id": "..." }}`.
- **v1** (the legacy `sms.arkesel.com/sms/api?action=send-sms` query-string API) returns
  `{"code": "ok", "message": "Successfully Send", "balance": 17706, "user": "..."}`, with numeric
  string codes on failure (`"102"` = Authentication Failed, `"109"` = Invalid Schedule Time).
  Community libraries key success off `code === "ok"` — but that is the **wrong generation** of the
  API for us, and copying it would silently mis-map every v2 response.
- Arkesel's own developer guide explicitly hedges, saying its shown request/response format is
  "illustrative" and must be verified against the official docs. Only the **HTTP status codes** are
  documented consistently: `200` success, `400` malformed body, `401` invalid/missing API key,
  `403` no permission (often an unregistered sender ID), `422` valid JSON but invalid data.

**Resulting design directive (binding for implementation):** treat the **HTTP status code as the
primary success signal** (`response.ok`). Parse the body only as best-effort enrichment — accept
`status === "success"` *or* `code === "ok"` if either is present, but never *require* either field,
and never let a missing/unparseable body turn a 200 into a failure or throw. This tolerates both
shapes and any third one, which is the only safe stance given the shape is unconfirmed.

### Arkesel v1 correction (supersedes the research section above)

The business owner supplied their **actual account's** API reference mid-run, and it is the
**legacy v1 query-string API**, not the v2 REST API the plan and TDD were designed against from
public-docs research. This was a real design change, not a tweak — the transport, auth mechanism,
and parameter names are all different:

| | v2 (designed, WRONG for this account) | **v1 (real)** |
|---|---|---|
| Method | `POST` | **`GET`** |
| Endpoint | `/api/v2/sms/send` | **`/sms/api?action=send-sms`** |
| Auth | `api-key` HTTP header | **`api_key` query parameter** |
| Payload | JSON body | **query-string params** |
| Recipient | `recipients: [...]` array | **`to=` single number** |
| Sender | `sender` body field | **`from=` param** |
| Message | `message` body field | **`sms=` param (URL-encoded)** |

**Verified live** with the real key via a read-only balance check — no SMS sent, no credits spent:
`GET /sms/api?action=check-balance&api_key=…&response=json` → HTTP 200, `application/json`,
`{"balance":523,"user":"Faazele Ishola","country":"Ghana"}`. So the key is valid, the account is
genuinely v1, and there are 523 credits available.

**The single most important detail this verification surfaced:** that balance response contains
**no `code` field at all**. The v1 envelope therefore varies by action, so `code` can never be
treated as guaranteed. Combined with the fact that query-string APIs like this commonly return
HTTP 200 even on logical failures, the success mapping must check **both** signals and require
**neither** field: fail on non-2xx, fail on a `code` present but not `"ok"`, and accept a 200 with
no recognizable `code` rather than throwing. This is stricter than the v2 design (which gated on
HTTP status alone) and is now encoded in the TDD.

Also resolved by this correction: `ARKESEL_SENDER_ID="Rostty"` is set and sender IDs auto-register
on the fly on this account — **no pre-approval step**, so the sender-ID prerequisite is closed.

Still not observed: the actual `send-sms` success body (reported as
`{code:"ok", message:"Successfully Send", balance, user}`). Confirming it requires a real send,
which costs credits and reaches a real phone — deliberately not automated, and not done without
explicit user sign-off.

## Design gaps found during pre-verification (handed to the spec agent as ground truth)

1. **The WhatsApp template needs an order shortId the notification layer never receives.**
   `notifyOrderStatusChange` (`src/lib/notifications/index.ts:11-19`) takes `orderId` (a UUID) and
   `orderDescription` — there is no `shortId` in the shape. The template's `{{2}}` is specified as
   the order shortId, and `AGENTS.md` mandates shortId in all user-facing strings. Both call sites
   (`src/app/admin/orders/actions.ts:116` and `:187`) already hold the order object, which has
   `shortId`. Resolving this requires widening the notification data shape.
2. **"Unconditional" ≠ "send to a null phone."** The locked decision removes primary/fallback
   branching between WhatsApp and SMS; it does not remove the `if (data.customerPhone)` guard at
   `index.ts:35`. Both channels fire independently *when a phone exists*.
3. **The plan's integration-test item is not achievable as written.** All six order-touching
   integration tests `vi.mock('@/lib/notifications')` wholesale, replacing the module — so they can
   never observe a WhatsApp call made *inside* `index.ts`. Fan-out assertions must live in a new
   unit test (`src/lib/notifications/index.test.ts`, mocking `./email`/`./sms`/`./whatsapp`);
   integration tests can only assert the call-site contract (that `ADMIN_ALERT_PHONE` now reaches
   `notifyLowStock`, and that `orderShortId` is passed).
4. **Webhook security specifics the plan left open** — raw body must be read with
   `request.text()` *before* any `JSON.parse` (consuming the stream first breaks HMAC);
   `crypto.timingSafeEqual` throws on length-mismatched buffers and needs a length guard; the
   route must stay on the Node runtime (not edge) for `crypto`; and the unset-secret behavior must
   be an explicit fail-closed decision. Next.js 16's own bundled docs
   (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/route.md`, "Webhooks")
   confirm `await request.text()` in a `POST(request: Request)` handler is the supported pattern
   and needs no `bodyParser` config.
5. A route test at `src/app/api/webhooks/whatsapp/route.test.ts` is **auto-discovered** by the unit
   config's `src/**/*.test.ts` glob (`vitest.config.mts:30`) — no config change needed.

   confirmed real and, on reflection, slightly higher-priority than "latent": every sender is
   contractually no-throw *today*, but nothing enforces that contract at the fan-out layer, and

   pass's mandate not to modify implementation code — flagging as the one item worth a deliberate
   yes/no decision (`Promise.allSettled`, or an explicit `try/catch` per channel) rather than
   silently accepting the convention, since it's cheap to close and the failure mode if it's ever
   wrong (WhatsApp silently stops firing) is exactly the kind of regression this feature's own
   "send both, always" product decision was written to prevent.
