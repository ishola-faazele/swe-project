## Key Design Risks (surfaced pre-spec)
1. ADMIN LOCKOUT RISK: src/app/auth/callback/route.ts looks up users by EMAIL
   (`findFirst({where:{email}})`) and only sets `id: user.id` (Supabase UUID) when creating a
   brand-new row. A user whose Prisma row already existed (seeded via prisma/seed.ts, or
   created through admin createCustomer) keeps a Prisma-generated UUID that does NOT match
   their Supabase auth UUID; the callback promotes their role but never reconciles the id.
   => requireAdmin() MUST resolve the Prisma user by id OR email, not id alone.
2. forbidden() / unauthorized() are EXPERIMENTAL in this Next.js version and require
   `experimental.authInterrupts` in next.config. Do NOT enable experimental flags; use plain
   throw / typed error returns instead.
3. Cancellation must be idempotent: only revert stock on a transition INTO CANCELLED from a
   non-CANCELLED status, or repeated calls will double-restore stock.

## Client Call-Site Audit (orchestrator, 2026-08-17) — drives the error-shape redesign
Every existing call site mutates local React state UNCONDITIONALLY after awaiting the action,
so a union return value breaks them in distinct ways. Verified line references:
- OrderClient.tsx:116-120  `const newOrder = await createOrder(...)` then
  `setData([{ ...newOrder, customer: c, ingredientLogs: [] }, ...data])` — spreads the return
  value directly; a wrapper object renders a blank table row.
- OrderClient.tsx:68-69  `await updateOrderStatus(...)` then unconditionally sets the new status
  locally — a rejected transition would still appear applied in the UI.
- OrderClient.tsx:88-89  `await deleteOrder(...)` then unconditionally filters the row out.
- CustomerClient.tsx:115-116  `const newItem = await createCustomer(...)` then spreads it.
- CustomerClient.tsx:125-126  `const updatedItem = await updateCustomer(...)` then
  `.map(c => c.id === updatedItem.id ...)` — with a wrapper, `.id` is undefined and the edit
  silently no-ops.
- CustomerClient.tsx:92-95  `await deleteCustomer(...)` then unconditionally filters the row out
  — this is the worst case: the FK-constraint failure this phase is meant to surface would still
  make the row disappear from the table, implying success.
Every call site must therefore check the result before touching state, and surface the error.

### spec revision — 2026-08-17
Result: complete
Notes: BLOCKING CORRECTION to the spec's original error-handling design, raised by the
feature-pipeline orchestrator and verified independently before applying. Original design had
every action `throw` ActionError/AuthError on any failure. This was wrong: Next.js redacts a
thrown Error's `.message` from Server Actions/Components in production
(node_modules/next/dist/docs/.../file-conventions/error.md — generic message + digest only) and
explicitly prescribes returning expected errors as values instead of throwing
(node_modules/next/dist/docs/01-app/01-getting-started/10-error-handling.md, "Handling expected
errors" -> "Server Functions"). Both citations confirmed by direct read. Redesigned:
- All 10 mutating actions now return `ActionResult<T> = {ok:true,data:T} | {ok:false,error:string,
  code:ActionErrorCode}` (new src/lib/errors.ts) for expected/business failures (insufficient
  stock, FK-referenced delete, validation, invalid CANCELLED transitions).
- Auth failures (requireAdmin()) still `throw` AuthError — kept in the "uncaught exception"
  bucket deliberately (matches Next's own categorization + every one of its own authz code
  samples + is impossible to accidentally bypass at a call site, unlike a forgotten `if
  (!result.ok)` check).
- getOrders/getInventoryItems/getCustomers now also require requireAdmin() (throws; unchanged
  return shape) — resolved from an open question to mandatory scope; orchestrator verified all
  three are called exclusively from already admin-gated page.tsx Server Components, and the
  customer dashboard queries Prisma directly instead, so this closes a real PII leak with zero
  risk to the customer path.
- Every one of the 10 call sites across OrderClient.tsx (3), OrderDetailsClient.tsx (2),
  InventoryClient.tsx (2), and CustomerClient.tsx (3) now needs a `result.ok` check before
  touching `result.data`, PLUS an outer try/catch for the AuthError case (event handlers aren't
  covered by React error boundaries per error-handling.md) — full before/after code specified per
  call site in the TDD's "Frontend Changes" section, matching the orchestrator's own
  Client-Call-Site-Audit findings above line-for-line.
- Added: z.array(...).max(50, ...) on both ingredient arrays (createOrder,
  updateOrderIngredients) — closes a previously-open question, cheap to add alongside other zod
  work.
- PRD's Open Questions trimmed: the alert()-is-acceptable and root-cause-ID-reconciliation
  questions are resolved (alert() confirmed fine, no toast; ID reconciliation confirmed out of
